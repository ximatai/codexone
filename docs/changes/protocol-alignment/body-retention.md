# 在途正文合计容量

让普通正文的合计驻留量与已确认的大正文容量、小请求可用性保持一致。

## 设计

所有普通正文从接收开始计量，完整解析后仍由执行 owner 保留 lease 至完成/丢弃；不以单条正文大小免除合计容量约束。共享容量保持 64 MiB，另设合计 8 MiB 小请求余量，仅允许总大小不超过 8 MiB 的普通正文使用。合格小请求优先使用余量，余量不足再使用共享，避免因小请求先到而无谓挡住两条最大正文；控制正文仍使用共享容量，不扩大控制授权。

单条 32 MiB、每连接 WS 队列 48 MiB、四个空 lease 等待者和五秒期限不变。空 lease 在可用容量不足时等待或明确 503；部分输入增长不持有部分容量排队。增长跨越分类边界时在同一预算锁内迁移预留，失败保留原预留供 owner 释放，不双重计算或先释放后冒险接纳。共享等待遵守既有 FIFO，小请求余量只服务小请求等待顺序，不被大请求堵住。

这不增加模型/Key 权限，不改变派发、配额、重放、schema 或恢复语义。回退会恢复旧容量解释，不能承诺仍具备本轮的合计驻留保证。

## 验收

验证共享与小请求余量的合计上界、独立池释放、空等待 FIFO/超时/取消、增长迁移失败、控制请求边界，以及 HTTP/原生 WS 的真实接收、断连和再次服务。保留双 32 MiB 与近 8 MiB 普通请求并存的验收，Linux 优化候选仍须通过实际 768 MiB 资源门禁。
