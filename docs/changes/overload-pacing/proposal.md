# 上游过载节流

拟把上游过载（5xx）的固定 15 秒账号模型冷却改为按连续次数递增的节流，单账号与多账号统一；429 限流与 401 认证屏障保持原样。

## 问题

[I20 账号执行健康](../../reference/specs/identity.md#i20账号执行健康与被动额度-owner)对 429 与 5xx 按模型冷却，缺省 Retry-After 时 5xx 默认 15 秒。冷却期内该账号模型不能准入；没有其他候选时新请求直接返回 503 account_unavailable。

上游 `server_is_overloaded` 是服务端整体繁忙，并非某个账号异常，下一次请求往往就能成功：

- 单账号：Codex 客户端遇 503 会短间隔自动重试，重试落入冷却期全部被本地拒绝，一次上游失败被放大为十余次本地失败并耗尽客户端重试。实际流量中曾出现上游 2 次过载、本地额外拒绝 30 次。
- 多账号：换账号仍访问同一上游，过载时各账号陆续被冷却，最终同样落入无候选拒绝；偶发一次过载即让账号离开 15 秒，并把流量和额度消耗推向其他账号。

真正属于账号的信号是 429 限流（及 401），此时冷却并改选其他账号才有意义。

## 范围

1. **过载节流**：`upstreamUnavailable` 且没有可信 Retry-After 时，账号模型进入节流期，按连续次数取 1、2、4、8、15 秒。任一成功执行清零；节流期过后未再失败不再阻断。连续计数为进程内状态，重启清零；持久冷却记录的截止时间按节流期写入，保持 attention/观察可见且不新增 schema。
2. **选择**：新请求优先选择不在节流/冷却中的健康账号。所有候选仅因过载节流不可用时，选节流最早结束者：剩余不超过 3 秒则在网关内等待到期后重新完整选择与准入；超过 3 秒返回现有 503，并带剩余秒数（向上取整）的 retry-after。
3. **等待边界**：等待在建立 intent 前，不占 Key 的 active/请求计数；客户端取消、请求期限或关闭立即结束等待，不计账号健康故障。同时等待的请求数有命名上限，超出按现有容量错误拒绝。
4. **有可信 Retry-After 的 5xx**：以其为截止；剩余不超过 3 秒同样可等待，否则 503 带 retry-after。
5. **不变**：429 限流冷却（缺省 30 秒或 Retry-After）与改选、401 认证版本屏障、额度与 Key 限额、账号并发、已持久准入/固定连接不跨账号重放均保持原样。readiness 以同一规则判断，过载节流已过的账号视为可用。

## 不做

- 用户可配置节流参数；网关自动重放上游已失败的请求。
- 改变 429 或认证失败的处理。

## 验收

- 单账号：过载后节流期内请求等待后转发成功；连续过载等待逐级增加至 15 秒；成功后清零；剩余超过 3 秒返回 503 与 retry-after。
- 多账号：过载账号在节流期内被避开、期满即可再选；全部节流时等待最早结束者；429 冷却账号仍被避开改选。
- 等待中取消/断开不建 intent、不记健康故障；等待上限；Retry-After 被遵守；401 不变。
- HTTP 与 WebSocket 入口一致；规范同步 identity I20 与相关说明；完整后端验证。

## 迁移与回退

无 schema 变化，连续计数仅在内存。回退旧版本即恢复固定 15 秒冷却，已写入的较短截止时间旧版本可直接读取，无数据影响。
