## 大 JSON 测量

2026-11-19，macOS arm64、Swift 6.4.2。用 `swiftc -O` 单独编译项目的 JSON 解析与编码源码，复用 `verify_mixed_capacity.py` 的扁平和结构化正文。每个版本和样本各启动五次独立进程，解析后释放入站 `Data` 再编码，取中位数。RSS 为 `getrusage` 在对应阶段结束时读取的进程历史峰值，含样本载入。所有样本在新旧版本重新编码后逐字节一致。

| 样本 | 解析耗时（ms） | 解析结束峰值 RSS（MiB） | 编码结束峰值 RSS（MiB） |
| --- | ---: | ---: | ---: |
| 9 MiB 扁平 | 33.2 → 15.7 | 32.9 → 23.8 | 48.0 → 38.9 |
| 32 MiB 扁平 | 116.9 → 53.9 | 101.9 → 69.8 | 158.0 → 125.9 |
| 64 MiB 扁平 | 229.5 → 109.8 | 197.9 → 133.8 | 310.0 → 246.0 |
| 64 MiB 结构化 | 335.2 → 208.5 | 222.1 → 158.0 | 332.9 → 269.0 |

旧实现 64 MiB 结构化样本的深度遍历约 164 ms，恢复键顺序前还分配一份 64 MiB 副本。两次遍历改为在 `withUnsafeBytes` 作用域内借用字节，UTF-16/32 继续按原规则转成 UTF-8，Foundation 仍决定接受范围、重复键与数值语义。这组测量仅覆盖单进程 JSON 路径，Linux amd64 的整机容量、cgroup 和回稳仍由现有容量检查验证。

同机复跑 29 项定向 Swift 测试、既有 HTTP/WS 字节顺序夹具和三轮混合容量演练，均通过。只在现有差分语料加入含 UTF-8 BOM 的 `Data` 切片，覆盖借用缓冲的偏移边界。无新增 CI 入口。

整体复盘收敛了上传初始化、HTTP 编码协商和容量夹具中的重复代码。macOS arm64 复跑 40 项定向 Swift 测试、既有 zstd 矩阵、两套契约的 WebSocket 完整边界及字节顺序检查、三轮混合容量演练，均通过。415 的重发仍使用同一份编码字节和原执行准入。

PR 复核后，HTTP 交换最终退出时清空编码正文，晚到的明文读取失败，入站 owner 仍负责兜底归还租约。复用既有 zstd 单元测试，加入真实正文预算和竞争租约，覆盖提前接受编码、压缩 EOF 后仍待协商、415 明文重发和最终 EOF 放行。macOS arm64 上 30 项定向 Swift 测试与既有 zstd socket 矩阵通过，CI 入口和 socket 场景数保持原样。

## 大正文暂存原型

2026-11-19，在本机 Docker 的 Linux arm64 虚拟机测量独立 SwiftNIO 原型。Swift 6.4.1 优化构建，每组新启动三个容器，限制 768 MiB、1 CPU、无 swap，使用项目现有的合成正文、共享预算及 JSON 解码。对照组整份预留 64 MiB 共享池，实验组将大正文分块写入独立 96 MiB 暂存配额，比较普通读取和只读 mmap 两种完整校验方式。文件在打开后立即解除目录链接，进程内串行执行大请求 JSON 校验。小请求继续走内存，在大请求接收与校验期间重复探测。

| 并行上传 | 模式 | 完成 / 发起 | 容量 503 | 接收中匿名 / 文件内存（MiB） | 容器峰值（MiB） | 小请求 p95（ms） | 进程写入（MiB） |
| --- | --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 × 40 MiB | 整份预留 | 3 / 3 | 0 | 34 / 3 | 90 | 5.1 | 0 |
| 1 × 40 MiB | 暂存后读入 | 3 / 3 | 0 | 7 / 27 | 131 | 4.2 | 40 |
| 1 × 40 MiB | 暂存后 mmap | 3 / 3 | 0 | 7 / 27 | 89 | 4.0 | 40 |
| 2 × 40 MiB | 整份预留 | 3 / 6 | 3 | 34 / 3 | 89 | 4.6 | 0 |
| 2 × 40 MiB | 暂存后读入 | 6 / 6 | 0 | 9 / 51 | 173 | 4.4 | 80 |
| 2 × 40 MiB | 暂存后 mmap | 6 / 6 | 0 | 9 / 51 | 131 | 5.0 | 80 |

容量以外各列取三轮中位数；p95 是各轮 p95 的中位数。接收中数据来自 cgroup `memory.stat`，容器峰值为 `memory.peak`，均包含内核计入该容器的文件页缓存。进程写入为 `/proc/1/io` 的 `write_bytes`，两个暂存方案的 `read_bytes` 都为零，此次校验由热页缓存服务。双上传原方案只完成一笔，容器峰值的对比不能视为同等完成量。上传断连和完整但非法的 JSON 均归还暂存配额，暂存目录没有残留文件名。

结果支持拆开接收期的 RAM 与暂存额度，也显示直接将文件读回一份匿名缓冲会抬高全容器峰值。mmap 降低了这份重复开销，完整 JSON 树仍存在。原型只在读完并通过项目 JSON 解码后返回合成确认，未接上游转发、业务授权、账本或 415，未验证真实正文的静态加密、文件回收与数据目录策略。未改生产路径、线上配置或 CI。下一步在接入前验证增量校验与必要改写能维持键顺序、准入和重发契约，并比较限速条件下的上传期限。若两笔 40 MiB 客户端入站共用 3 Mbps，仅传输就至少约 224 秒，显著超过现有 120 秒总期限。此原型使用回环网络，无法据此推定线上慢上传会成功。

后续把协议合成原型留在测试目标中。入站文件在长度、实际 `ResponseRequest` 解析和模拟授权通过后关闭，按实际订阅契约生成的编码字节进入另一份匿名暂存，由现有 `HTTPUploadPayload` 持有。回退使用相同映射，编码确定且上传到 EOF 后归还额度。macOS arm64 上 4 项定向 Swift 测试覆盖 8 个输入，验证短正文、非法 JSON、模拟权限拒绝、取消和写失败时的派发与回收，以及压缩、明文重读的精确字节。复跑既有 `twice415` 真实 socket 单场景，确认现行网关只做一次明文重发。此轮只验证原型与现有组件的交接，生产鉴权和实际账本、存储加密及完整接线留待后续，未增加 CI 入口或集成矩阵。

同版接入后，生产实现以独立的 192 MiB 额度、每文件随机 AES-GCM 密钥和有界 worker 取代合成 mmap 原型。复用生产鉴权、请求准备、Core 准入和结算，保留无配置时的原路径。macOS 定向测试、既有加密 zstd 回退场景及混合容量演练通过。容量演练原有首轮改用两笔 40 MiB，在两端分别已发送 24 MiB 后开放上传屏障，三轮和上游派发数保持原样。Linux amd64 资源峰值和回稳由现有发布候选检查确认。
