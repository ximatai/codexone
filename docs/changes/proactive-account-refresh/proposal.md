# 账号访问凭证提前刷新

日期：2026-10-31。修改[身份规范](../../specs/identity.md) I20 的后台刷新触发时机与托管 dispatch 的过期判定。

## 问题

订阅账号的访问凭证目前只在**过期之后**刷新：后台额度观察或请求准入发现凭证已过期，才交给共享刷新 owner。因此：

- 过期那一刻到达的请求要同步等待一次刷新；
- 凭证在剩余几秒时被选中派发，上游连接可能在建立前后就遇到过期；
- 管理台看不到凭证何时到期、何时刷新过，无法判断保活是否正常。

官方 Codex 客户端在访问凭证剩余不足 5 分钟时就主动刷新（无法解析到期时间时按 8 天周期）。本网关的凭证始终带到期时间，只需引入提前窗口。

## 行为

- 后台周期（现有 60 秒）对 enabled/draining 且 ready 的账号：访问凭证剩余有效期不超过 **15 分钟**时，交给现有共享刷新 owner 刷新，不新建刷新语义。窗口大于周期，过期前有多次机会。
- 托管 dispatch：剩余有效期不超过 **5 分钟**的凭证按需要刷新处理（与官方客户端一致），走现有 dispatch 刷新路径。已持久准入和固定连接不受影响，不跨账号重放。
- 提前刷新失败：
  - 网络/超时等未发出或明确未完成：凭证仍有效则保持 ready，下个周期再试；
  - 提供者明确拒绝或旋转结果不确定：维持现有 requires_auth / auth_uncertain 语义，不循环使用旧刷新令牌。
- disabled 账号不做后台提前刷新（维持现状：仅手动观察）。
- 管理接口与账号详情显示访问凭证到期时间与最近一次凭证更新时间（授权或刷新），只用现有持久数据，不显示令牌内容；无可靠来源的字段显示不可用，不新增 schema。
- 结构化日志记录提前刷新的开始与结果（账号标识、凭证版本、结果分类），不含凭证。

## 代价

刷新次数略增：每个访问凭证周期最多提前 15 分钟刷新一次。刷新令牌旋转的单飞、CAS 与崩溃后 auth_uncertain 保护不变。

## 验收

- 合成提供者：剩余 >15 分钟不刷新；进入窗口后后台刷新一次，凭证版本 +1，并发与重复周期不重复刷新。
- dispatch 遇到剩余 ≤5 分钟的凭证先刷新再派发；刷新失败时返回现有错误分类，不派发旧凭证。
- 提前刷新网络失败保持 ready 并在下周期重试；提供者拒绝进入 requires_auth；结果不确定进入 auth_uncertain。
- disabled 账号不被后台刷新。
- 管理接口返回到期与最近更新时间，不含任何凭证材料；前端账号详情显示。
- 执行者完整 `verify.sh --backend` 与 `--web --chrome`；主 Agent Linux verification；部署后在测试实例确认真实刷新发生（凭证版本递增、无请求失败）。
