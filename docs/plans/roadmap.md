# 项目里程碑计划

以可验收的能力闭环推进 CodexOne：先把核心正确性和主要使用路径做实，再完成首版产品，最后按证据扩展。每个里程碑都应能够验收、停止扩展并交接，不以代码量、目录齐全或演示成功作为完成依据。

本文只维护目标、顺序与阶段边界；当前所处阶段、完成情况和验证结果统一见根 [STATUS](../../STATUS.md)。产品范围与行为分别以 [产品目标](../requirements/product.md) 和 [能力规范](../specs/README.md) 为准；本文不新增协议或另立行为规则。计划可以根据实践调整，影响产品承诺的取舍须及时沟通并同步相应文档。

## 推进原则

1. **先纵向闭环，再增加维度。** 从无凭证基础、持久执行、单身份协议，推进到多账号与多主体；不同时铺开所有业务。
2. **先证明不变量，再扩大兼容面。** 身份归属、持久屏障、未知执行、取消和结算随能力一起交付，不留到发布前补做。
3. **最小管理能力随业务进入。** 某阶段需要配置、认证、禁用或诊断时，同时提供必要入口；完整管理体验在后续收敛，避免前期被页面数量牵引。
4. **关键未知尽早核实，扩展性议题后置。** 可能推翻首版承诺的假设要提前验证；泛化框架、多上游、多节点等议题不阻塞核心闭环。
5. **阶段有出口，问题有去向。** 验收不通过就修复或明确调整目标，不用下一阶段功能掩盖问题。阶段内的新需求先判断是否影响出口，其余进入后续阶段。

## 阶段总览

| 阶段 | 目标 | 收敛出口 |
|---|---|---|
| M0 工程基座 | 可运行、可测试、可交接 | 从干净环境完成构建与无凭证验证 |
| M1 持久执行内核 | 执行状态与资源治理经得起失败和重启 | 真实 SQLite 与进程故障验证关键不变量 |
| M2 单身份协议闭环 | 一组主体与账号跑通 Desktop 文本/工具/压缩与传输路径 | 明确客户端版本的实际协议验证及失败证据 |
| M3 账号池与权限治理 | 多账号、多主体可以安全使用和管理 | 隔离、刷新、调度、限额与订阅额度观测 |
| M4 图片能力闭环 | 图片生成/参考图编辑成为可授权的产品能力 | generation/edits 实际入口与统一权限验证 |
| M5 有限恢复闭环 | 缓存对应可使用、可解释的恢复路径 | 客户端契约、加密容量与故障验证 |
| M6 首版产品与发行 | 自托管用户能够安装、管理并替代现有服务 | 弱服务器发行、迁移与回退验收 |
| M7 需求驱动的扩展 | 基于真实使用证据演进产品 | 每项扩展独立立项和验收 |

M0—M6 共同交付首版目标，中间的单账号或单能力切片不缩减首版范围。M7 是后续方向，不是首版完成条件，也不承诺全部实现。

## M0：工程基座

**目标：** 建立后端、前端与测试的最小可运行结构，使后续能力有稳定承载和验证入口。

**重点与交付：**

- Swift Core / Adapters / Runtime / 入口的依赖方向、严格并发与锁定依赖。
- 数据面与管理面健康入口、配置校验、服务监督、退出和端口释放。
- React/TypeScript/Vite 管理台外壳，以及单元、协议、进程和浏览器测试入口。
- 无凭证 CI、目录职责和 Agent 接手入口。

**边界：** 不把健康检查当作代理功能；不接真实账号，不实现账本、账号池或业务管理页面。不为未来能力预建插件系统或大量空模块。

**验收出口：** 干净环境可按文档构建、运行和验证；部分启动失败、取消与未完成连接均能收敛；执行未配置时明确拒绝业务请求。CI 定义与远端实际通过须分别说明。

## M1：持久执行内核

**目标：** 先建立不会因断线、竞争或重启而丢失执行责任的最小内核。

**重点与交付：**

- SQLite 版本化 schema、连接初始化、迁移与核心原子事务。
- 准入、资源预留、发送 intent、ID 归属持久屏障和幂等结算。
- 已知用量、估算与未知执行暴露的区分；重启后 pending/exposure 的保守处理。
- 应用用例、持久化适配器与 Runtime 的任务所有权和结束路径。

**边界：** 使用合成主体、账号和上游执行，不接 OAuth 或真实模型。只实现支撑执行不变量的最小数据结构，不建设通用任务平台、报表系统或恢复正文库。

**验收出口：** 在真实临时 SQLite 和进程重启中验证竞争准入、重复结算、库不可写、关键屏障前后失败与未知执行；不得把可能已执行的请求自动重发或退款。迁移有验证，网络调用不跨数据库事务持锁。

## M2：单身份协议闭环

**目标：** 在一个主体、一个 Key、一个上游身份的受控切片中，跑通以 Codex Desktop 为主的真实使用路径，CLI 提供补充证据。

**重点与交付：**

- 将 M1 内核接入 HTTP/SSE/WebSocket 数据面；按 [P11](../specs/protocol.md) 验证 Desktop 的模型目录/选择、文本、客户端函数工具、连接预热、压缩和续接。
- 验证 `/v1` 与现有 `/backend-api/codex` 接入路径、认证头及模型元数据；覆盖 HTTP 直连、HTTP→WS 桥接兼容和原生 WS 的外部行为，不限定内部照搬旧实现。
- 提供本切片所需的最小安全配置、认证与脱敏诊断，不要求完整管理界面。
- 验证取消、慢客户端、背压、空闲断开、上游提前关闭、错误 envelope 和重试边界。
- 对照明确的客户端版本核实续接与恢复入口：关联什么 ID、由谁读取已有输出、何时只能由客户端重建。形成支持范围与不可用情形的结论，供 M5 使用。

**边界：** 不做多账号调度、完整授权管理、图片生成或正文缓存实现；不承诺兼容所有 Codex 版本。默认采用合成上游，真实订阅调用须在明确授权下单独验收，不能用 fixture 成功代替。

**验收出口：** 真实 socket 测试证明协议与持久执行结合正确；在获授权的明确版本 Desktop 中完成模型选择、文本、工具、预热、压缩和续接闭环；HTTP 直连/桥接及原生 WS 分别验收，并能解释断线后的执行责任，不能只凭 CLI 成功通过。恢复可行性核实必须收敛为明确结论；若首版恢复目标缺少可用客户端路径，及时提交证据与取舍，不靠自行发明私有协议跳过问题。

## M3：账号池与权限治理

**目标：** 将单身份闭环扩展为可管理、相互隔离的多账号和多主体产品能力。

**重点与交付：**

- 订阅账号接入、授权刷新、凭证安全保存、单飞刷新与版本冲突处理。
- 多 principal/Key 的创建、禁用、权限配置，以及请求/并发限制和用量解释。
- 按 [U10](../specs/usage.md) 建立订阅窗口额度/重置观测及按 Key 统计查询；区分上游余额、本地治理与费用估算，明确陈旧/不可用数据。
- 账号选择、健康处理及故障转移；续接归属、文件/私有 ID 和 WebSocket 身份约束优先于调度。
- 必要的账号与 Key 管理 API/界面，使隔离、禁用和异常处理可以通过产品入口验收。

**边界：** 单管理员管理域、单节点；只做订阅账号池，不扩展公开 API 上游、计费支付、多管理员 RBAC 或复杂路由规则语言。金额继续作为估算，不承诺 token/金额绝对封顶。

**验收出口：** 跨主体/账号引用被拒绝；会话不会因重试切换身份；刷新竞争、禁用、部分失败、限额竞争和未知执行暴露均有回归验证。管理员可以解释请求的归属、拒绝原因、订阅额度/重置与按 Key 用量状态；故障注入不会留下失去 owner 的任务。

## M4：图片能力闭环

**目标：** 在已完成的身份和治理体系上交付图片生成与参考图编辑，保住现有客户端的两类使用效果，并保持图片权限独立。

**重点与交付：**

- 原生 Images generation、edits（参考图编辑）入口及 Responses 图片工具；按 [P12](../specs/protocol.md) 验证参数、图片/multipart 输入和适用返回/流式行为，上游可采用经验证的工具适配。
- 图片生成权限独立于对话模型白名单；generation/edits 和 Responses 工具使用一致授权与用量治理，关闭生成不误伤视觉输入。
- 图片负载、响应大小、取消、错误和未知执行处理；管理表单与诊断呈现相同权限含义。

**边界：** edits 限定为已验证客户端需要的参考图编辑组合，不承诺全部参数与扩展；不建设相册、永久作品库或通用文件托管；不因临时失败静默切换到另一个计费来源，也不自动重新生成。

**验收出口：** 在实际产品入口验证允许/拒绝、模型限制与图片权限组合、视觉输入和异常响应；获授权的 Desktop 能够完成生成、带参考图编辑及连续主动编辑；后续主动编辑是新执行，不能与断线恢复混为一谈。大负载和断线不破坏内存有界、身份归属和执行结算。

## M5：有限恢复闭环

**目标：** 为已验证的客户端路径提供限期限量的恢复能力，明确可恢复与不可恢复的情形。

**重点与交付：**

- 基于 M2 核实的客户端契约接入恢复，明确适用客户端/版本、关联方式、读取语义与错误行为；按 [C11](../specs/recovery-cache.md) 对照旧服务的下游断开、上游关闭、进程重启与续接丢失效果。
- 正文/图片加密、密钥版本与独立管理、按主体和执行归属校验，以及 TTL、容量和删除。
- 写入队列、物理文件/WAL 与在途内存有界；容量压力下缓存先退让，保障核心状态写入与结算。
- 重启、备份恢复代际、删除与写入竞态；诊断不泄露正文或凭证。

**边界：** 不承诺任意断线无损恢复，不建设托管历史产品；缓存默认不进入备份。已有输出可读取不代表客户端已经消费，更不代表工具没有执行；恢复不自动重跑模型或工具。

**验收出口：** 从实际客户端恢复操作开始验收，覆盖可用、过期、删除、权限变化、容量不足与恢复旧快照。证明加密隔离及资源上限有效，并逐项说明能恢复已有输出、保持续接或需客户端重建的条件及差异；安全重试原则不因追求表面等效而放宽。如果契约不可行，先沟通调整范围，不能以“正文已经存下”代替恢复交付。

## M6：首版产品与发行

**目标：** 将前面闭环整合为普通自托管使用者可安装、可管理、可维护的首个正式版本。

**重点与交付：**

- 完成安全初始化、管理认证和账号/Key/权限/用量/诊断界面的端到端操作体验；包括订阅额度/重置、按 Key 时间范围用量/趋势及错误筛选，不照搬无关图表。
- GitHub CI 构建 Linux amd64 OCI 镜像，Compose 安装与配置；服务器只运行产物。
- 在前述迁移与密钥机制之上完成升级、备份、恢复、维护模式和回退演练，明确数据兼容与不可直接降级的情形。
- 明确客户端兼容范围、配置说明、资源要求、用量/恢复限制和故障处理指南。
- 按 [O14](../specs/operations.md) 在约 1.6 GiB 内存的参考宿主或可解释等效环境验证混合负载、图片编辑峰值、断流、缓存与低磁盘压力，给宿主及共存服务留余量。
- 按 [O13](../specs/operations.md) 演练 CodexLB 替代：现有域名/路径、账号接入、Key 保留或换发、客户端变更、存量会话边界、切换与回退；不共享数据库，不无协调刷新同一凭证。

**边界：** 以单节点可靠本地磁盘部署为发行目标；不同时承诺多架构、多节点、所有历史版本升级或无人值守迁移。发布准备不等于自动替换用户服务器上的旧服务，真实迁移单独安排。

**验收出口：** 新使用者按文档完成安装、接入账号、发放 Key、文本/工具/图片生成及编辑使用与故障处理；真实 Linux 发行、弱服务器容量、迁移及恢复/回退演练通过，关键权限/故障路径纳入回归。现有使用效果逐项验收，不能以新安装成功代替旧服务可替换；迁移差异须在切换前说明并确认。说明验证平台、负载范围与已知限制；不把本机通过写成云端 CI 或生产部署通过。

## M7：需求驱动的扩展

**目标：** 依据首版实际使用和维护证据选择投入方向，形成技术积累，不提前承诺扩展清单。

候选方向包括公开 API 等独立上游适配、超出首版 generation/参考图 edits 的图片扩展、更广客户端兼容、更多发行平台、调度优化，以及确有需求时的多管理域或高可用。此处允许探索，但每项工作仍需有具体使用场景、预期收益、维护成本与独立验收目标。

**边界：** 不为候选方向提前重构为插件平台或分布式系统；不把所有候选项打包成一个无法结束的“大下一版”。涉及信任域、隐私、成本或恢复承诺的变化重新讨论，不沿用首版结论自动扩张。

**验收出口：** 每次只推进有证据支持的扩展；验证后明确采纳、暂缓或放弃。采纳的方向拆成新的有限里程碑，同步规范和架构，不长期保留并行讨论稿。

## 首版替代验收归属

以下是 [产品替代基线](../requirements/product.md) 的阶段分配，不是另一套行为规范；详细约束仍以对应条款为准。

| 使用效果 | 首要阶段 | 最终验收依据 |
|---|---|---|
| Desktop 模型选择、文本/工具、预热/压缩/续接与 HTTP/WS/桥接 | M2 | P11；M6 在目标反代下复验 |
| 多 Key 共享订阅、独立权限、账号刷新与订阅额度 | M3 | identity、U10、A08/A09 |
| 图片生成、参考图编辑及权限一致 | M4 | P12、I03/I09 |
| 断线/重启后的恢复边界和差异 | M2 核实，M5 实现 | C10/C11；不以自动重执行凑齐效果 |
| 按 Key 统计/趋势与请求错误诊断 | M3 数据能力，M6 完整交互 | U10、A03/A08 |
| 原域名/路径、账号/Key 迁移、存量会话及切回旧服务 | M6 | O13；真实切换另经授权 |
| 弱服务器混合负载与磁盘压力下有界运行 | 各阶段保持有界，M6 综合验收 | O14；公布实测范围与限制 |

## 阶段切换与范围控制

- 2026-10-22 用户明确允许：保留 M2 Desktop 界面验收和恢复契约缺口，不标完成，先推进不依赖它们的 M3。此例外不关闭 M2，也不解除 M4/M5 的实际客户端或恢复契约验收要求。
- 2026-10-22 用户进一步授权：保留 M2/M4 Desktop 和真实订阅兼容缺口；M5 先核实恢复读取契约，不足时明确记录证据/边界，不标完成，并推进不依赖它的 M6 工作。此例外不改变 C10/C11 与首版替代验收要求。
- 默认按 M0 → M6 的依赖顺序推进。文档整理、测试夹具和后续需求收集可以并行，但不得绕过前置正确性验收。
- 开始一个阶段时，按 [变更约定](../changes/README.md) 将其拆为有限任务，明确入口、外部可观察结果、失败用例和排除项。里程碑不要求一个大提交或一个大变更。
- 结束阶段时，用实际验证证据对照出口，说明未覆盖条件，更新 STATUS 并交接下一切片。通用约束引用规范，不复制多套检查清单。
- 只把阻塞当前出口的问题纳入本阶段。新想法和非必要泛化归入 M7；发现会推翻首版可行性的证据则立即沟通，不能作为“以后探索”拖延。
- 调整阶段时说明问题、证据、推荐方案及对后续阶段的影响；归纳后的决定更新对应正式文档，过程由 Git 历史追溯。本文不设未经测量的容量、工期或固定发布日期。
