# CodexOne 架构与目录独立审查

日期：2026-10-21。对象：正式项目当前工作树；独立意见，不代表已批准实施。

## 结论与边界

建议保留模块化单体、SQLite 单节点和窄 NIO 数据面。现阶段没有证据支持换框架、引入服务拆分或扩展插件框架。核心持久屏障、未知执行与网络资源分账、恢复缓存可降级的方向有长期价值。

主要风险不是缺少更多目录，而是**运行责任和构建边界尚未定型，详细契约仍散落在架构中，以及缓存首发承诺尚未落到具体客户端恢复协议**。这些风险值得在相应切片开始前收敛；不能把“尚无实现”本身当成架构失败。

审查读取 AGENTS/README/STATUS/HANDOFF、产品/规范/ADR、当前架构、目录/治理/验证、路线和 M1 提案任务、检查脚本及实际 Git 跟踪目录。未读取旧 codex-lb 或原型源码，未访问服务器/账号、安装依赖或运行不存在的构建。所有判断均基于本仓库静态证据，未做外部协议事实验证。

## 必须现在调整：少量契约与治理问题

### R1 · P1：将首发恢复能力收敛到至少一个具体客户端契约

**证据：** [产品范围](../requirements/product.md) 把正文恢复缓存列为首版闭环；[C02/C05](../specs/recovery-cache.md) 要求可靠 operation 标识及接收位置，没有则 unavailable；[架构 §9.1](../architecture/ARCHITECTURE.md#91-短期正文恢复缓存用户已确认首发) 同时允许完整输出重放、重复提交识别及同身份续接，但未指定哪个客户端、入口、标识和读取协议真正提供这些信息。[路线](../plans/roadmap.md) 到 M3 才验证缓存。

**反例与影响：** 一个只发普通 POST、断开后再发新 POST 的客户端，没有稳定重试标识；一个 WS 重连客户端只有 previous_response_id，没有最后已收序号。按现有安全规则，两者都可能只能返回 unavailable。即使加密、TTL、删除和容量全部实现，仍可能没有一个可用恢复产品路径。这是交付定义缺口，不是要求放弃已决定的首发缓存。

**建议：** 现在补一张很小的首发恢复验收表：受支持客户端/版本、恢复入口、关联依据、完整结果取回或断点续播、授权规则、不可恢复条件。把“至少一种经验证路径”的出口条件写入 M3；在重型缓存实现前先用合成客户端验证该契约。若标准客户端不能承载，明确是否提供显式、受限的恢复调用，不能自行偷偷增加公共历史 API。无需预建通用恢复协议。

### R2 · P2：消除当前规范与架构之间的双事实来源

**证据：** [规范索引](../specs/README.md) 宣称规范定义当前行为，却把详细状态机指向架构。架构独有大量可验收约束，例如 §4 单次 finalizer 移交后的 mergeEvidence、§6 刷新成功后落库失败的处理、§9 绑定与账本保留策略；规范只有概要。架构 §1/§11 仍有“已有 Linux CI”等原型语境，末尾又写“后续将本稿转为正式规范”，而 STATUS 已说明规范已建立、正式 CI 尚无。

**反例与影响：** 新 Agent 只按 U04 写结算，遗漏迟到证据槽关闭条件；另一个 Agent 只改架构细则，规范审查无法发现契约变化。优先级规则不能解决规范不完整的问题。

**建议：** 将安全/持久性/恢复的强制细则逐步落入对应规范的子条款或规范附表；架构保留状态图、取舍和对规范编号的引用，不再复制第二份强制正文。现在先清除当前架构的迁入时态歧义，并把“详细状态机哪些是规范”标清。不必一次重排全部历史设计；历史快照继续保留不覆写。

## 首个相关实现时调整：形成可执行边界

### R3 · P1：为跨模块运行责任写一页 owner/端口表，避免 Runtime 成为业务中心

**证据：** [目录约定](../development/layout.md) 规定 Application 拥有事务边界、Runtime 负责最终化/恢复；[架构 §3–§6](../architecture/ARCHITECTURE.md) 又将连接 supervisor、刷新、finalizer、策略快照和数据库事务分散描述，尚未明确谁调用谁及谁拥有可变状态。

**反例与影响：** Application 等 Runtime finalizer，Runtime 为结算又调 Application；Transport 依赖 Runtime 取 ticket，Runtime 又持有 Transport 具体 channel。代码可编译成单 target，却形成难以测试的循环与关闭死锁。把所有服务塞入一个全局 actor 也会让 DB 等待拖住流量。

**建议：** M1 只为实际切片列 owner、调用方向、寿命、取消/关闭责任：Application 决定准入/结算/绑定业务状态与事务；Persistence 用显式命令执行原子 SQL；Runtime 承担监督和调度生命周期；Transport 持连接并提供有界写出/关闭能力；入口负责组装。端口和跨层值类型由使用者一侧定义，NIO channel、SQL row、Vapor Request 不进入领域/应用签名。finalizer 的业务事务与其后台 task owner 应分开描述。用一条 DB 不可写加客户端断连路径验证，避免先画完整类图或给每个函数建协议。

### R4 · P2：将客户端协议与上游提供者适配分开，避免通用 Responses 模型吞掉差异

**证据：** [架构 §3](../architecture/ARCHITECTURE.md) 将 Protocol/Upstream 合并说明解析、认证、归属及 usage；[目录约定](../development/layout.md) 分为两个目录，却未定客户端模型、上游 wire 模型和可暴露事件分类的边界。

**反例与影响：** 未来公开 API 上游与订阅上游都叫 Responses，但错误、usage、私有 ID 和能力不同；一套共享 DTO 加大量 optional/布尔值会让不支持组合落入透传，或迫使新增上游修改 Transport/账本。

**建议：** M2 首个真实适配器形成“客户端校验 → 小型应用命令 → 提供者 wire 协议”的方向；保留原始字段仅在有界协议层使用。由提供者适配器输出对象绑定、usage、终态、可重试证据等语义；Application 决定是否发布/结算，Transport 不认识提供者名称。能力表先用静态数据和合成差异夹具证明，不创建插件注册器、通用路由 DSL 或庞大统一 AI schema。首发仍只实现订阅提供者。

### R5 · P1：核心库与缓存库必须有不同的持久性责任及 I/O 配额

**证据：** [目录约定](../development/layout.md) 把账本、归属、缓存均放 Persistence；[架构 §9.1](../architecture/ARCHITECTURE.md#91-短期正文恢复缓存用户已确认首发) 已明确独立 SQLite 缓存、缓存失败可降级、低磁盘优先清缓存，但未给核心 finalizer 与缓存写任务共享 DB/加密执行资源时的调度边界。

**反例与影响：** 即使两个数据库文件分开，缓存图片加密和批量删除占满同一有限线程池，结算无法取得执行槽；同一磁盘已满时，“再清缓存”也不当然保证结算 WAL 可增长。两个库也不能被误当成一个原子事务。

**建议：** M1 事务端口按准入/绑定/结算业务原子命令设计，避免通用逐表 repository 迫使上层拼事务。M3 再实现 RecoveryStore，应用层负责恢复授权与跨库流程，Persistence 只承接原子条件写；为核心写入保留执行容量并限制缓存批次/优先级，具体实现可先用同池配额，无需增加独立服务。用“缓存队列饱和/清理/磁盘故障时核心结算仍有机会完成”验证，而不是只测缓存自身吞吐。core generation 的创建、缓存隔离和恢复次序必须有一个应用用例 owner。

### R6 · P2：SwiftPM 目录按真实 target 落地，检查脚本不要冻结占位树

**证据：** 当前没有 Package.swift，所有预留目录均由 Git 跟踪 .gitkeep，故 clone 不会丢目录。[layout](../development/layout.md) 明确九个目录只是逻辑边界；但 [check_docs.py](../../scripts/check_docs.py) 的 DIRECTORIES 强制要求这些目录及 Unit/Integration/Contract/EndToEnd，未来调整结构反而失败。

**影响与建议：** M1 确定少量必要 target，按 target 放 Sources/Tests，并在测试 target 内按 Unit/Integration 等分类，或显式声明测试 target/path；不要让目录名自行决定九个库及四个测试 target。逻辑层可以先作为实际 target 内子目录，消失的占位目录同步删除，脚本改为校验当前清单。Protocol 作为目录可以保留，正式模块命名时选清晰的产品名，减少 generic import 歧义；无需现在重命名空树。

脚本另用 ROOT.rglob('*.md') 扫全树，未来 node_modules/.build/产物中的第三方 Markdown 会被当成项目文档检查。随包初始化改为受控项目路径或明确排除构建/依赖目录。该检查只能证明结构，不能充当规范追溯或语义验证。

### R7 · P2：前端按管理能力聚合，但共享契约必须先于大管理台

**证据：** [web/README](../../web/README.md) 只有 src/tests；[A02/A03](../specs/control-plane.md) 已要求有效策略、未知成本与核对。路线 M4 才做管理台。

**建议：** 当前空结构不构成缺陷。M2/M3 出现最小管理 API 时固定错误 envelope、ID、日期/用量单位、权限继承及 secret write-only 字段；M4 按账号、Key/策略、请求/用量、恢复/运维能力聚合 UI/API hooks/测试，共享区只放已有复用组件与 API 客户端。不要先建全套 components/services/hooks/types 横切目录或复制 Swift 领域对象作前端状态。由契约夹具或实际选定工具约束两端，暂不强求 OpenAPI 生成体系。安全会话、前后端同源静态服务/代理边界随首个管理入口验收，不能等到发行时才发现双监听端口被错误暴露。

## 以后触发再做

| 触发条件 | 动作与长期收益 | 现在不做的理由 |
|---|---|---|
| 第二个真实上游进入开发 | 用能力/差异夹具验证 adapter 边界，必要时提取复用协议组件 | 首发只有一个真实提供者，合成差异足够暴露耦合 |
| Swift target 的编译时间、依赖污染或并行维护成为实测问题 | 再拆 target，保留现有单向依赖 | 逻辑目录已经足够表达职责，九 target 不是产品能力 |
| 账本/未结项长期积累或低磁盘阈值逼近 | 明确账本归档、备份保留和诊断清理工具，证明不破坏幂等/恢复 | 不需要现在引入分区、外部数据仓库；但应列为发行容量验收项 |
| 需要多节点/HA，或单 writer 实测不可接受 | 按既有架构做数据迁移设计与停机/回滚演练 | 不为假设扩展预建通用 ORM/多数据库层 |
| 正式远程/首次可执行发行确定 | 加安全私密报告入口、支持版本、依赖更新/漏洞响应、构建来源与 Linux 升级夹具 | 现在未确认远程，不能填虚假入口；也不应推迟到发现首个漏洞后 |

## 优先行动与验证

1. 现在补首发恢复契约最小表，清除规范/架构当前时态及责任归属歧义。
2. M1 先实现一条真实临时库垂直路径；同时形成 target 依赖、事务命令和 owner 表，以代码证据决定目录。
3. M2/M3 用差异夹具和缓存/主库组合故障验证边界；随后才扩大管理界面。

本报告没有发现应阻止 M1 开始的技术栈问题。无 Package.swift、锁文件、CI、迁移、管理台及发布配置均是已公开的待实现项，不另记“缺陷”；真正需提前处理的是交付定义和责任模糊，不能靠新增目录补齐。

实际验证：读取 Git 状态与 git ls-files 核实正式分支、未修改的基线及占位目录可交接；新增本报告后运行 python3 scripts/check_docs.py，仅验证本地文档基础。无服务构建、协议、性能或安全测试结果。
