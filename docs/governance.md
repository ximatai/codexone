# 项目治理

## 单一状态入口与文档职责

| 位置 | 维护内容 | 更新时机 |
|---|---|---|
| STATUS.md | 全局阶段、下一步、阻塞、远程、可运行命令及最新验证 | 有意义的进展/交接 |
| README / 各目录 README / HANDOFF | 稳定定位、职责、阅读入口、协作方法 | 定位或组织方式变化 |
| requirements / specs | 产品范围草案、单一行为契约 | 对应需求/行为改变 |
| architecture | 组织、依赖、运行责任及取舍，引用规范 | 结构或责任改变 |
| decisions | 方案选择的理由、代价与替代历史 | 有实质决策或替代 |
| changes | 任务细节与带日期验证证据 | 对应变更推进 |
| reviews / evidence | 有日期、不可冒充实时状态的审查/实验记录 | 新增记录，历史不覆写 |

不要为一次小工作同步所有文档。STATUS 不复制完整任务清单；tasks 是各变更的验收进度，不是另一份全局状态。历史证据里的“当时通过”无需随产品进展改写。链接与导航可以引用 STATUS，不能复制状态内容。

## 草案与调整

产品边界、架构、规范和 ADR 为可演进工作基线。按基线实现和验收；发现不可行、更高成本或更优方案，及时说明证据、影响、选项与推荐。常规工程选择自主推进，无副作用验证可先做；涉及外部行为、隐私/额度/恢复或重大范围变化时与用户沟通后更新契约，不能默默改口，也不能用旧草案阻止讨论。

文档冲突要同步消除。行为条款只在规范完整定义，架构以编号引用及解释，不另设第二套强制细则。已发布兼容承诺若需调整，按版本/迁移流程处理，草案阶段也不能伪称兼容已验证。

## 变更与决策

行为、协议、安全、schema 等改变先建/更新 docs/changes/<slug>/proposal.md 与 tasks.md，注明目标、排除项、规范引用、验收和数据影响。完成记录实际验证。纯文案/结构整理无需额外流程包装。Markdown 工作流不要求专用 CLI。

ADR 记录工作假设而非禁令；替代时保留旧理由并明确 superseded/新 ADR，或在草案阶段标明修订日期与原因，不重写历史评审。

## 质量、发行与维护

PR 聚焦可验收能力，关键并发/持久/恢复改动覆盖部分失败，UI 提供关键流程与截图。验证应报告范围和局限，不以目录或检查脚本通过宣称产品能力。

依赖按需引入、锁版本与许可证；发布提供可追溯源码/镜像、升级/备份/回退证据。公开安全报告入口、支持版本与依赖响应随发行准备确定，不填写虚假联系人。部署/推送与真实账号使用按用户授权执行，凭证泄露报告只留脱敏复现。
