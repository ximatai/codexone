# 项目治理

## 事实来源与变更

产品范围定义首版；docs/specs 定义可验收行为；ADR 记录长期取舍；当前架构解释实现组织。STATUS 是进度唯一入口，任务细节在 docs/changes。发生冲突由执行者同步修正并说明，不得通过文档优先级掩盖矛盾。

行为变更先建 proposal.md/tasks.md（模板在 changes/_template），说明需求、非目标、契约影响、验证及回退。实现后同步规范，并记录实际验证结果。规范变化引用变更目录；关键技术取舍追加编号 ADR，已有决定被替代时标 superseded 并相互链接，历史评审不重写。

轻量 Markdown 工作流先行，暂不引入 OpenSpec 命令或额外文档平台。将来改工具必须保持文档和交接可读，不把工具安装变成理解产品的先决条件。

## 贡献与质量

每个 PR 聚焦一个可验收能力，包含相应规范和外部失败路径回归。安全边界、持久化/迁移、并发资源与恢复变更必须覆盖故障分支。CI 尚未建立前明确报告本地验证范围；不能声称远程检查或独立评审已经通过。面向 UI 的改动交付可审阅截图及关键流程验证。

外部依赖在需要时添加、记录来源和许可证并锁版本，不为预期扩展引入框架。允许常规工程决策自主推进；新增副作用、改变隐私/额度/恢复承诺必须明确告知用户。

## 发布与运维

首发 Linux amd64 OCI/Compose，通过 CI 构建；部署机器不编译。发布需可追溯源码、锁文件、无凭证测试、镜像标识、备份恢复与回退验证。部署/发布必须有明确授权。数据库升级与旧快照恢复是不同动作，不以恢复旧余额作为自动回退策略。

版本支持与安全报告入口随远程仓库确定；当前不填写未经确认的邮箱或开公共漏洞工单。凭证泄露先停止扩散、通知拥有者并撤销/轮换，报告只留脱敏复现；禁止把真实登录材料提交作测试 fixture。
