# 多账号路由治理讨论稿

CodexOne 面向个人自托管，管理本人订阅账号，为自己的设备和工具分发 Key。订阅池继续自动选路，设备 Key 无需预绑账号。客户端体验以真实 Codex 直连对照为基线。本文记录后续专项讨论，已生效规则见[身份与路由规范](../reference/specs/identity.md)。

## 现状

- 新请求从符合 Key 权限、账号健康和并发条件的候选中选择。存在软亲和时优先沿用原账号，其余按在途请求数排序，并列时稳定打散。剩余额度与重置时间尚未纳入选路排名。
- 上游对象、可信续接状态或已绑定连接限定归属账号。仅有会话提示时是软偏好，原账号不可用时后续请求可能选到其他账号。
- 短时过载可在准入前等待。生成路径的普通限流和明确订阅额度耗尽目前共用限流分类，影响后续选路。可能已执行的请求保留原执行责任。

## 三类策略

| 策略 | 决定什么 | 适用场景与代价 |
| --- | --- | --- |
| 故障转移 | 首选账号遇到哪类故障时允许改选，恢复后何时重新纳入选择 | 适合临时网络故障、服务过载或并发饱和。需要区分派发前失败、明确拒绝和结果未知，也要区分过载、额度耗尽和访问限制。 |
| 按剩余额度与重置时间分配 | 多个健康账号都可用时，怎样分配新流量 | 适合不同套餐和不同重置窗口。需要明确短窗和长窗冲突时的目标，以及快照陈旧、字段缺失和并发选中同一账号时的退化规则。 |
| 按优先级排序 | 多个健康账号都可用时，按用户意图先用哪个 | 适合主用账号加备用账号，选路容易解释。需要讨论恢复后是否立即回切，以及回切是否只影响新会话。 |

三类策略可以组合。先按请求权限、账号归属与健康状态确定候选，再对可选账号排序，最后依据具体失败类型决定能否重新选择。同一请求的重试与后续请求的选路分别判断。

## 专项待决问题

1. 默认目标是稳定使用主账号、均衡消耗，还是优先使用更早重置的可用额度？何时需要运营者可见的优先级？
2. 有软亲和的会话遇到并发满、临时过载、普通限流、明确额度耗尽或访问拒绝时，分别应等待、返回原因还是为后续请求改选？全新会话单独确定规则。
3. 配额按账号、模型还是更宽范围判断？何种新鲜度和完整度的额度数据可以参与排序，缺少可信数据时采用哪个基线？
4. 原账号恢复后，已经迁移的软亲和会话是否回切？短时间状态反复变化时如何减少切换？
5. 管理员需要看到哪些选路原因，例如原账号、入选原因、拒绝类别和恢复时间？诊断只记录解释决策所需的字段。

## 后续验收

业务规则确认后，再按[变更流程](../changes/README.md)记录协议、数据与回退影响。先用少量合成用例覆盖正常选择、原账号阻断、强归属拒绝和派发后断流。涉及客户端可见行为时，用实际 Codex 做直连与经网关对照。验收同时检查账号归属、重试次数和用量结算。
