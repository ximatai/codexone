# CodexOne 修订架构聚焦复核

日期：2026-10-21。对象：`ARCHITECTURE.md` 当前 254 行版本。保留原设计与原评审，不修改二者。本次只读取修订文档，沿用此前已独立核查的一手协议资料，没有读取旧源码、实验报告或调用真实账号。根代理提供的 CLI 原生出图、NIO 断连实验和现有发行基础视为有范围的输入事实，不在本次重复验证。

## 结论

**修订方向可采用；B1、B2、B4、B5 和关键 I 约束已在设计层闭环，B3 仍需修改。** 设计闭环不代表实现已经通过验收。窄 NIO 数据面已确定、独立 Images generation 首发、CLI 仅外部测试客户端，这三项修订与新增事实一致，无需重新选型或重复询问用户。

§7 的“每个首发组合必须有可信最坏上界 U，否则不启用”仍是一个发布阻断条件。它虽未要求按 U 全额预留，不能严格等同完整硬预算算法，却**把严格成本保证所需的证据变成所有功能的启用门槛**，与已确认的订阅账号池优先、资源治理而非严格 billing 方向冲突。建议删除这一通用门槛，保留有证据才声明数值上界的规则。修正后可进入正式规范与任务，无需再扩写一轮总架构。

## 唯一需要先改的原则：U 不能成为订阅账号池通用准入门槛

**优先级：P1。位置：** §1 L15、§7 L151–167、§11 L223、§12 L237、L254。

### 为什么当前规则会阻塞核心流程

订阅后端的增量 `previous_response_id`、压缩上下文、图片输入、推理输出或图片 generation，可能无法给出可验证的完整 token/金额最坏值。请求声明的模型名、输出参数或图片尺寸并不自动证明实际执行上界；公开 API 参数也不能替订阅后端作证。对此保持不确定性是正确的。

但修订稿由此得出“没有 U 不启用”，会导致已优先选择的订阅工作流在没有成本证明时被整体拒绝。尤其 L163 还将缺少 usage 的组合直接排除；订阅侧若只有部分 usage 或只有额度窗口信息，首发可能变成“必须先补齐类似收费 API 的计量能力，才可使用账号池”。这是额外的产品限制，不是实现正确性的必要条件。

**我对原评审 B3 的澄清：** 无可靠上界时拒绝，是针对严格 token/金额预算组合的建议。用户既已选择资源治理，就不应继续把该拒绝条件推广到全部首发组合。有限次数不能证明有限金额，这个数学事实应限制宣传口径，而不是迫使产品升级为严格 billing。

### 四类量必须分别承诺

| 量 | 首版可以承诺什么 | 不能由它推出什么 |
|---|---|---|
| 本地连接、队列字节、任务、活动 turn | 本地硬上限，超限拒绝；资源生命周期可验证 | socket 关闭即上游停止、额度停止消耗 |
| 未确认执行数量 | 每 principal/identity/全局限制；断线不释放 exposure ticket，达到阈值断路 | 单个执行 token/金额有可信上界；上游实际并发永远已知 |
| 本地 token/图片/credit 治理 | 已知实测用量准确追加；估算/未知分开；按 R 控制预留及新准入 | 本地 credit 就是订阅真实剩余额度；本地窗口就是上游限流窗口 |
| token/金额最坏上界 U | 仅有后端证据的组合可计算并显示数值上界 | 所有订阅能力都必须有 U；没有 U 就一定不能提供有限资源的网关 |

以“每张图片固定若干 credit”可以约束**本地业务单位**，但不能因此声称图片 token、官方用量或真实费用有界。反过来，也无需因为无法证明真实费用而禁止这种明确标注的本地计数治理。

### 务实默认建议

1. `U` 保留为可选证据，**不作为治理模式通用启用条件**。支持组合首先由协议、身份归属、安全、取消与资源生命周期是否已验证决定。没有 U 的组合可启用，但 UI/诊断明确“成本上界未知”。
2. 保留 `used + held + R <= B` 的本地准入规则，R 是公开的运营预留策略，不假称真实最大值。已知 usage 超 R 时如实记账并按治理阈值停止新准入；token 用量只能部分取得时标 partial/unavailable，绝不按零补齐。
3. `known usage`、`estimated usage`、`unresolved usage` 分字段，不能把估算写进真实用量列。无可信 usage 时，可使用明确命名的请求/图片/业务 credit 单位治理；token 预算显示不可用或仅已知部分，并继续执行请求数、并发、大小和未知数量控制。
4. 每 principal/identity/全局硬限制活动 turn、unsettled exposure、请求速率、排队字节及图片并发；任何未知执行保留 exposure 和相应预留，达到数量、占用或年龄政策即断路。**不靠无限自动到期退款来保持可用。** 这是真正防反复断线扩大风险的机制。
5. 将“有界超额风险”改为准确表述：**资源和未确认执行数量有界；成本风险受准入及断路治理，但没有 U 的组合不承诺 token/金额超额数值上界。** 不向用户暗示总成本已经数学有界。
6. 若某能力真的完全无法判断执行归属、重复执行风险或结束证据，仍可因这些协议/生命周期缺陷禁用；不能把“没有计费 U”与这些缺陷混为一谈。未知 usage 本身也不应永久占网络/active 槽，而应归 unsettled exposure。

这不是取消限额，也不是声称估算足够安全；它将可证明的工程限制和无法证明的真实成本保证分开，符合已确认的资源治理范围。默认建议直接据此修订规范，不再要求用户审批每个工程控制。

### 一个应同时修正的公式细节 / P2

L165 给出 `sum(max(U-R,0)) + 既有已知 overage` 的细化界，需要精确定义才能使用。超额结算可能已吃掉其他未决请求的预留空间，此时只看 `used-B` 与各自 `U-R` 会漏算。例如当前 used=90、B=100、一个未决 R=U=20，最终可能到 110，但上述两项都可能为零。

若每个未决执行都有 U，且 used 只含已结算实际值，可展示 `max(0, used + sum(U_unsettled) - B)`；若未决已有部分入账，则只加各自未计入的剩余上界，避免重复。混有 U 未知项时直接显示“无法给出总体成本上界”。该展示公式不应进入无 U 组合的功能门槛。

## 仍真正需要用户取舍的内容

- **短期内容缓存：** 是否允许请求正文/图片只在内存中短期保留、目的是什么、是否跨请求/断线使用、TTL 和字节上限。正常传输所需的有界缓冲与额外历史缓存应明确区分；不持久落盘不代表没有内容留存。默认建议仅保留当前执行必须的缓冲，连接终止即清理，暂不额外缓存历史。若为了恢复而缓存，另定恢复范围及工具副作用边界。
- **未知成本与恢复的可用性政策：** 保留预留并达到阈值断路时，管理员如何释放/计收及承担未知成本；旧快照默认冻结受影响窗口的建议是否采用。可先用保守运营默认，不需要用户逐个批准具体并发数字。

订阅账号池优先、单管理员管理域、资源治理、独立 Images generation 首发、窄 NIO 数据面和 CLI 角色均已有决定，不再列为开放问题。将无 U 时的宣传口径改准确，是遵守资源治理决定；只有用户额外要求“所有组合的 token/金额超额都必须有可证明数值上界”时，才需说明这会拒绝部分订阅流程并形成新的业务取舍。

本次未运行代码/测试，也未声称官方 API 文档可以证明订阅后端的 U 或 usage。修订稿中的官方协议链接沿用原评审已核查的 [WebSocket](https://developers.openai.com/api/docs/guides/websocket-mode)、[Background](https://developers.openai.com/api/docs/guides/background) 与 [SQLite synchronous](https://www.sqlite.org/pragma.html#pragma_synchronous) 证据范围；本次关键结论是对文档内约束的一致性与风险保证范围的逻辑复核。
