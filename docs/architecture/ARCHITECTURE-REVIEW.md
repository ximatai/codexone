# CodexOne 架构独立审查

审查日期：2026-10-21。审查对象：`PROPOSED-ARCHITECTURE.md` 当前 349 行版本。下文行号均指该版本；原稿未修改。

本审查只读取项目根 `AGENTS.md`、设计稿及独立核查的一手资料，没有读取旧项目、原型实现、实验报告或此前设计讨论，没有访问凭证、真实账号或现有部署。结论是设计审查，不是代码审计或性能验证。

## 结论

**建议有条件采用 Swift + Vapor/NIO + SQLite 的模块化单体方向，但本稿还不能直接作为首版实施契约。** 没有发现必须换语言、上微服务或首发 PostgreSQL 的理由。账号所有权、保守重试、未知用量及正文不留存的立场合理；下面 5 个 P1 缺口应在正式实现前补成状态机和验收条件，其中前两个直接影响多账号续接正确性。

这里的“阻断”指阻断对外承诺及相应热路径设计定稿，不阻断无凭证的传输/事务验证。其余首版约束可以在实施任务中落实，不需要把全部细节继续堆进总架构稿。没有证据支持 P0 级已发生漏洞。

## 必须先修正的设计缺口

### B1 / P1：WS 在知道首个请求归属之前无法正确固定账号

**位置：** §3 L47、L52；§6 L145–153；§7 L157–165；§16 L309。

**触发：** 客户端重新建立 WS，首个 `response.create` 带属于 U1 的 `previous_response_id=R1`。若握手阶段按负载先连接 U2，第一个 turn 就无法续接；握手时又没有该字段可用于选 U1。此问题也发生于先经 HTTP 获得 R1 再切 WS。设计同时要求“整个连接固定身份”和“按全部引用对象归属调度”，但没有首次绑定时序。并发到达的首批不同 lane 还会竞争固定身份。

**影响：** 不能兑现声明的同身份恢复；实现者容易退化成错误跨账号转发，或把本可恢复的会话拒绝。若握手即占执行槽，空闲连接还会吃光生成容量。

**修正：** 推荐下游握手只完成本地认证和独立连接容量准入，`ConnectionContext` 初始为 unbound；在有界首消息期限内验证第一个 create、解析所有对象归属、准入并原子绑定身份，随后建立上游 WS。首批消息串行经过绑定状态机，后续 lane 的归属必须匹配。模型/工具资格也在此时选择，不能只凭握手选账号。若指定客户端要求握手即验证上游，需明确替代产品限制，而不能假定透明成立。另列连接租约与活动 turn 租约。

**验收：** HTTP→WS 续接、跨连接重连、两个首 lane 竞争不同归属、首消息超时、无额度但可建立下游连接；均不得错误访问另一身份。

### B2 / P1：绑定“观察后创建”没有规定必须先于对外暴露持久化

**位置：** §3 L47、L53；§7 L157；§9 L195–199；§10 L225。

**触发：** 已转发 `response.created` 的 R1，绑定写库尚未完成时进程被 kill，或绑定写入遇磁盘满。客户端已保存 R1，重启后网关只剩 attempt intent，不知道这个 ID 的主体/账号。另一种情况是同进程客户端立刻跨 lane 分叉，先于异步绑定提交。

**影响：** fail-closed 会让成功收到 ID 的客户端丢失续接；“未知 ID 试一下账号池”则破坏隔离。原始字节透明转发与可靠所有权之间有一个目前未定义的提交屏障。

**修正：** 第一次包含可引用 ID 的事件必须先经过有界识别窗口，持久化 `(subject, identity namespace, object ID, attempt)` 后再向客户端暴露该 ID；内存发布也服从该顺序。绑定失败停止转发并进入可恢复未知状态，绝不重放执行。对普通 JSON 和图片/容器文件等被允许返回的可引用对象采用同一规则，或明确将其后续引用标为不支持。不要求每个 delta 写库。

**验收：** 在绑定提交前后、事件写出前后分别 kill；暴露过的 ID 重启后必须可判定归属，未暴露 ID 的执行成本仍可进入 pending。加入跨 lane 立即引用夹具。

### B3 / P1：首版“token 预算”仍缺可实施的预留算法

**位置：** §2 L40；§7 L159–165；§9 L189–211；§17 L326。

**触发：** `previous_response_id` 只传新输入，上游却加载历史；conversation、图片 URL/文件、工具执行继续扩展上下文。网关不留正文且未读取完整上游上下文，无法仅由当前请求估出完整输入上界。`max_output_tokens` 限输出，不单独解决这些输入与工具成本。按上一轮 usage 加当前输入也不是通用可靠上界。

**影响：** 要么普通 Codex 多轮请求大量被严格预算拒绝，要么不足额预留后超限。稿中承认货币硬上限限制，但同样的问题会影响默认推荐的 token 硬预算；不能把它留成一句“可验证输入上界”。

**修正：** 发布前为每种首发模型/输入/工具提供预算模式表。默认建议：请求/并发是硬限；token 为已知用量治理加有上限的预留风险，并明确标示允许的超额；若坚持 token 硬限，则用能力声明的保守整窗上界等可证明方法预留，不能证明的组合拒绝。需锁定缺失输出上限、模型别名变化、图像/文件展开、工具轮数和实际用量超过预留的处理。不能在输出已产生后靠停流撤销已经发生的用量。

**验收：** 同余额并发、长历史增量续接、图片输入、工具循环、计价/策略窗口切换、实际值超过预留；余额不下溢且 UI 准确区分硬限与治理。公开 API schema 对 conversation 自动加入上下文和输出上限有明确说明，见 [S2]；不将其外推到其他后端。

### B4 / P1：Responses 允许字段中存在不同执行模型，不能统一按前台 turn 处理

**位置：** §2 L31；§6 L126–128、L151；§9 L195–201；§11 L241。

**触发：** HTTP 接收 `background=true`，普通 JSON 返回 queued/in_progress 后执行仍继续；首版却未承诺 GET/cancel，后台工作也未列出这类执行的持续所有者。WS 的 `generate:false` 则会建立可续接响应状态但不返回模型输出，不能按“无生成终态即异常”统一处理。官方还存在新增的控制功能；“有限理解”无法自动证明这些功能都不影响权限或记账。

**影响：** 后台响应可能长期占预留或失去并发控制；错误释放槽会导致实际生成超过限制。warmup 会错误占用额度、丢失谱系，或被误判不确定。

**修正：** 首版明确拒绝 HTTP background，以及未实现生命周期的控制事件；不要悄悄改写字段。对已选 Codex 版本若需要 `generate:false`，单独规定 warmup 准入、速率/状态容量、绑定及无 usage 的结算规则。建立 endpoint × transport × execution mode × tool 的封闭能力组合表；未知普通元数据可透传，未知执行控制默认拒绝。远端 MCP、文件检索/容器等工具默认关闭，直到外部对象归属、工具成本和权限有契约；“支持工具调用”应明确首先是客户端执行的 function tools。

**验收：** background 不能到达首发上游；warmup 后正常续接；未知控制事件不能绕过 turn 准入；未授权工具无法执行。官方 background 文档明确支持轮询、取消和断流后继续生成 [S3]；WS 文档明确支持 warmup [S1]，schema 声明 WS 不支持 background [S2]。

### B5 / P1：durable intent 的保证没有绑定 SQLite 持久性配置及恢复边界

**位置：** §5 L112–114；§9 L193–205；§10 L221–225；§15 L297–299。

**触发：** 使用 WAL + `synchronous=NORMAL` 时，准入事务已返回 commit，随后请求发往上游；主机掉电后该事务回滚。此时不是“活动 attempt 转 pending”，而是 attempt/预留本身消失。`kill -9` 夹具不能覆盖主机断电。另一个独立边界是恢复旧备份：快照后的已完成执行和预留都不会凭空恢复。

**影响：** 用户重复使用已花额度，网关没有 pending 可核对，所谓 durable 准入与恢复闭环不成立。WAL 本身不足以证明所需持久性。

**修正：** 推荐首版显式选择 WAL + `synchronous=FULL`，逐连接设置并验证 foreign_keys、busy 和所需 pragma；声明底层磁盘可靠同步是部署前提。若为性能改 NORMAL，必须明确只保证进程崩溃恢复并接受主机故障后的额度风险。恢复快照进入 maintenance/reconciliation 状态，展示备份时间与缺失区间；由管理员确认恢复后的预算基线后启用准入，不能仅将快照内活动请求转 pending 就自动 ready。

**验收：** 检查实际连接配置，覆盖 commit 后故障恢复与旧快照恢复流程；将应用 kill 和系统/存储故障分开列证据。SQLite 明确说明 NORMAL/WAL 的已提交事务可能因掉电回滚，而 FULL/WAL 提供持久性 [S4]；外键启用状态应显式验证 [S5]。不宣称这些设置能抵御失信磁盘或修复备份缺口。

## 首版实施约束

以下问题不要求改掉总体架构，但必须进入实施任务和发布门槛。

### I1 / P1：不确定执行的“网络槽”和“成本暴露”必须分开

**位置：** §9 L195–213；§11 L231、L241；§14 L281。

断线后 socket/本地任务可以释放，不能据此认为上游并发已释放。反复制造断线可在账号上留下许多未确认停止的生成，同时本地不断发新请求。金额/token 预留不等于并发保护，请求速率也不覆盖长期未知积累。

要求分别记录 transport lease、active turn、unsettled execution exposure；给每主体/身份的未知执行数量和预留总量设置断路阈值，超过后禁止新执行并提供手工处理。上游没有查询能力时明确“无法自动核对”，不是无限自动重试的后台任务。释放额度与手工更正必须有原因、操作者和业务唯一键。验收重复断线直到阈值、迟到终态与管理员调整竞争。

### I2 / P1：稳定身份不可通过改 origin/凭证悄悄指向另一个实际账号

**位置：** §7 L157–159；§8 L175–181、L185；§10 L219。

管理员将身份 U1 的凭证换成实际账号 U2，或改 Provider origin/project 后，旧绑定仍引用 U1；刷新 CAS 只防版本覆盖，不能证明身份等价。要求凭证导入/刷新校验提供者身份及组织/项目命名空间；无法验证时显式建立新 identity 并排空旧 identity。origin、project 或稳定身份的语义变更必须迁移/失效旧绑定，不能普通 CRUD。账号删除先 tombstone，保证历史账本可解释。

若后端采用轮换 refresh token，还需规定刷新成功但新密文提交失败/主机中断的状态：旧 token 可能已不可用，单飞/CAS 不能修复；标记需重新授权，不能无穷刷新。此为条件风险，未假定某个具体提供者必然采用一次性刷新令牌。

### I3 / P1：有界 finalization 不能在已执行后因队列满而丢失

**位置：** §9 L195–199、L213；§10 L223；§11 L231–235。

必须在 dispatch 前保证后续最终化有可识别 durable intent；finalizer 移交不能只是向一个可能已满的内存队列发送终态。定义重复完成、取消、runtime shutdown 的单次移交协议，队列满时阻止新准入并靠既存 held/attempt 恢复。DB 已失败时无法再写 pending，故恢复必须能从已有 held/dispatching 识别待核对项，而不依赖失败时那次写入成功。

任务退出顺序要避免 reader 等 writer、writer 等 finalizer、finalizer 等 connection actor 的循环等待。使用独立故障注入证明队列满、DB 不可写、客户端取消和 shutdown 同时发生仍收敛。

### I4 / P1：多 lane 的背压和本地拒绝必须有确定协议行为

**位置：** §6 L146–151；§11 L233–241；§16 L309、L313。

同一个上游 socket 不能简单给每 lane 启动独立 iterator；共享 writer 也不能让不同帧片段交错。单 lane 的排队错误与该 lane 前一个活动响应的事件可能交错，客户端能否正确关联必须测试；文档中的 `stream_id` 不是任意本地请求 ID。停整个 socket 的读取还会阻止其他 lane、ping/pong 和终态观察。

首版规定单 reader、串行帧 writer、按 lane 分派和连接总预算；定义慢消费者导致全连接终止的可接受条件，不能承诺 lane 级网络隔离。每个 task/actor mailbox 的入口也受预算约束，不能每帧创建一个 Task 再称队列有界。记录哪些阻塞通过关闭 channel 中断、哪些以任务取消中断，所有 continuation 必须恰好 resume 一次。

NIO 官方 producer 明确要求单 iterator、响应 stopProducing，并不建议依赖 deinit 清理 [S6]；这些是可实现的构件，不是 Vapor/WS 组合已经满足要求的证据。首版是否采用 Vapor 或窄 NIO 数据面仍需公开接口和 Linux socket 夹具决定，不能从本审查推导任选其一都已验证。

### I5 / P2：ID 命名空间与 TTL 清理仍缺生命周期契约

**位置：** §7 L157–165；§10 L217、L223；§15 L299。

服务端说 ID 不是全局唯一，但客户端只交原始 ID；同主体在两个命名空间出现相同字符串时必须拒绝歧义或提供已验证的别名机制，不能取第一条。绑定过期后未知 ID 必须 fail-closed，不能恢复为自由调度。保留的 TTL 应与上游对象寿命和承诺的续接窗口对齐，并向用户披露“上游仍保存但本地绑定过期”的失败。

分别定义 bindings、requests/attempts、audit、ledger 的保留和压缩规则；没有正文不代表数据不会增长。账本/未结项不可被普通 TTL 清理删除。给低磁盘阈值、备份空间、checkpoint/WAL 增长设告警与准入策略，防报表/备份将服务推到磁盘满。

### I6 / P2：升级发行还有两处可操作性缺口

**位置：** §15 L289–299；§17 L332。

systemd 安装路径需要对应的原生 Linux 发行资产、运行库/发行版要求和架构测试，不能只提供 OCI 镜像就称两条安装路径完整。默认建议 OCI/Compose 为首发受支持路径；原生 systemd 在同版本资产与恢复夹具齐全后纳入。

主密钥轮换应写出多 key version 共存、断点续加密、验证所有存量/备份所需 key、何时允许销毁旧 key；“密钥单独恢复”不足以避免旧备份永久不可读。CLI migration 必须与在线服务共享同一实例锁，并有清楚的版本兼容范围和失败退出行为。开源首发还需许可证、安全漏洞报告入口及支持版本政策；不必因此引入插件框架或多租户管理。

## 可延期且不应首版预建的内容

PostgreSQL、多实例 fencing/owner routing、托管完整历史、资产下载服务、细粒度 RBAC、独立 Images/文件端点、完整 tracing exporter 均可延期。现有“可替换边界”只应约束依赖方向，不应承诺无成本替换数据库/传输。

未来 PostgreSQL 迁移至少需要离线转换、ID/唯一约束保持、账本校验、停机切换和回滚，而不只是更换驱动；此刻记录触发指标即可，不需要首发实现。多个 actor 和约 17 张表本身不是过度设计证据；更值得压缩的是首发同时涵盖两种身份后端、太多工具组合或两条长期维护的数据面。Runtime actor 宜只处理控制面快照/任务索引，不要把每个 token/帧都串行送进去。

## 真正需要用户决定的业务取舍

| 决策 | 审查默认建议 | 为什么需要决定 |
|---|---|---|
| 首发究竟支持哪种上游身份 | 先锁一种身份类型；若产品价值依赖订阅账号池，应明确优先该类型，而不能拿公开 API 多 Key 适配替代验收 | 决定授权方式、额度来源和 Codex 实测协议；其余技术选择无法代替这个产品决定 |
| token 是否必须绝不超额 | 默认请求/并发硬限，token 用量治理允许披露且有界的超额，金额估算；严格模式单列可支持组合 | 不留正文、增量续接、工具与图片下，严守上界会牺牲容量利用率或拒绝请求 |
| 未知执行何时可继续使用账号/额度 | 默认保留预留，加未知数量/金额断路；超阈值需管理员审计处理 | 可用性与实际成本暴露之间无法仅靠算法消除取舍 |
| 正文留存与恢复 | 默认不留正文，允许无法续接时交给客户端重建 | 无需先做历史库，但 UI/宣传必须接受这一可用性限制 |
| 使用主体 | 默认同一管理员控制、多个稳定 principal 隔离，不首发公网 SaaS | 决定审计、滥用治理与隔离责任；共享账号不能默认为所有 Key 共享数据 |

其他问题如懒绑定、落库屏障、SQLite FULL、单 reader、取消所有权属于工程正确性约束，无需反复让用户批准。普通撤销允许在途完成、全 WS 固定账号、SQLite 单节点和图片路径可沿用原稿默认。

## 建议的收敛顺序

1. 确定上游类型、预算含义和首发 Codex 范围，补一页支持/拒绝组合表；明确 background、warmup、工具和对象引用。
2. 补 WS unbound→bound 时序与“绑定先于 ID 暴露”的故障边界；补预算和未知执行断路规则。
3. 确定 SQLite pragma、快照恢复准入流程，再做最小持久准入→执行→结算的垂直切片。
4. 在 Linux 无凭证夹具验证真实 socket 取消、队列峰值、多 lane 交错、DB 故障和崩溃恢复后，选择默认数据面。正式客户端/账号兼容必须另行授权实测，不由模拟结果代替。

不建议先完成整套管理台再回头解决这些边界。设计最有价值的资产应是可执行的不变量与兼容夹具；首版成功标准是一个明确支持的 Codex 工作流能安装、使用、诊断和恢复。
