# CodexOne 架构意见汇总

日期：2026-10-21。架构阶段文档；不代表实现或验收完成。没有修改 Ali 服务，没有新增真实账号调用，也没有推送本轮草案。

## 设计与审查过程

按项目所有者的要求，设计者只接收产品背景、目标和技术方向，以独立上下文编写 [原始设计](PROPOSED-ARCHITECTURE.md)。另一位独立审查者随后读取该设计并编写 [首轮评审](ARCHITECTURE-REVIEW.md)。二者起初均不读取旧实现及实验报告，避免把旧结构直接当成答案。

之后根代理提供已经验证的协议事实、实验边界和用户确认的业务方向，设计者形成 [修订架构](ARCHITECTURE.md)。原始设计与原始评审保留，避免用改写后的文档掩盖决策变化。[聚焦复核](ARCHITECTURE-REVIEW-FOLLOWUP.md) 已完成，发现的用量治理表述和少量恢复边界已纳入修订稿；用户于本轮确认短期正文恢复缓存及兼容优先治理，已更新实施基线；缓存新增设计已由独立评审定向复核，发布位置不确定性、重试关联、恢复代际隔离、删除防回填均已补齐；评审未发现新增重大架构问题。

## 已确认的产品边界

首发优先 Codex/ChatGPT 订阅账号池，支持自托管、单管理员管理域、多个上游身份与相互隔离的 Key/使用主体。公开 API 项目 Key 后续单独适配。

请求与并发采用硬限制，token/图片采用资源治理，金额明确为估算；不首发严格计费系统。用户已确认首发有上限、有期限的正文恢复缓存，正文与图片加密，固定期限及多级容量限制，默认不进入备份。兼容优先：允许正常 Codex 续接、图片和工具，控制并发与未知执行，超预算停止新准入，明确不保证 token/金额绝对封顶。

## 各方一致的技术方向

采用 Swift 6 严格并发、模块化单体、本地 SQLite 和静态管理 SPA。窄 NIO 数据面接 HTTP/WS/Images，Vapor 承担管理 API，AHC 使用长寿命客户端；领域规则不依赖 Web 框架。单机、小服务器优先，不提前引入多实例、Redis、消息系统或 PostgreSQL。SQLite 使用显式事务、WAL、FULL 和逐连接配置校验；其适用边界是本机可靠磁盘和单写服务。

核心设计资产是协议能力矩阵、身份与对象归属规则、有限状态机、背压与取消、幂等账本以及恢复契约。框架只是实现手段；Swift 的编译期并发检查不替代事务、生命周期测试或真实性能证据。

首轮评审的五个重点已经进入修订稿：WS 首次有效请求决定身份；可引用 ID 在暴露前持久绑定；预留、实际用量与未知执行分开；foreground/warmup/background 分开建模；掉电持久性和恢复旧快照的维护屏障明确化。独立复核确认其中归属、ID 屏障、执行模式及持久恢复的设计闭环；后续窄修订已解除通用 U 门槛，并补明重启 exposure、刷新不确定性和迟到用量合并约束；兼容优先运营模式现已由用户确认。

## 根代理的补充判断

1. 已有断连实验足以确定窄 NIO 数据面方向，不再重开 Vapor 与 NIO 的选型竞赛。正式实现仍要验证 Linux、HTTP keepalive 和部署反向代理，不能照搬实验中单连接单请求的限制来宣称生产完成。
2. 独立 Images generation 应纳入首版。实际 Codex 客户端原生出图使用该端点，只支持 Responses 内置图片工具不足以覆盖目标工作流。图片编辑和文件资产服务可以延期。
3. 对话模型范围与图片生成权限分开；关闭生成不应误伤截图/图片输入。Responses 图片工具与独立 Images 必须共用同一个生成权限规则。客户端 actor 声明不是认证凭证。
4. Codex CLI 是外部兼容测试客户端。服务器直接处理协议与调用上游，不依赖逐请求启动 CLI。真实客户端验证和无凭证契约测试是两类证据。
5. 不把有限并发描述成绝对 token/金额上限。未知执行保留预留并受数量与暴露阈值约束；断线不自动退款，也不证明上游已停止。用户已选择兼容优先，无可信 U 的组合应明确披露数值上限不可得，不施加通用的严格预算证据门槛。
6. 根代理原建议不持久保存正文；用户了解旧服务后选择首发短期恢复缓存，已按此选择修订。缓存不等于完整历史托管，更不授权不确定执行的自动重放。建议初始 24 小时、单操作 32 MiB、主体 128 MiB、实例 512 MiB，参数经容量测试定稿。旧服务事实见 [留存说明](LEGACY-RETENTION-NOTE.md)。
7. 首发安装路径收敛为 Linux amd64 OCI/Compose，用 GitHub CI 构建。ARM、原生 systemd 待独立验收后支持，不让弱服务器承担编译。现有 MIT 许可证继续沿用。
8. 首个内部垂直切片可以只接一个身份；正式首版仍须完成多账号、受限 Key、文本/工具/图片、管理诊断与备份恢复的产品闭环。实验回显接口不能直接充当公开产品。

## 后续实施收敛

业务边界已确认，短期缓存定向复核已完成；将架构作为实施基线，拆成按能力验收的任务：持久准入与结算骨架 → HTTP/WS 身份与会话 → 订阅账号池和图片 → 管理台与诊断 → 发行及恢复。

每一步的完成条件应是外部行为和故障场景证据，而非增加了多少模块：隔离正确、未安全证明执行失败不重放、断连后本地资源收敛、未知消耗不丢失、数据库故障不绕过屏障、旧快照不静默恢复过期额度。正式验收还包括 Linux 资源回稳与真实 Codex 兼容性；本轮文档不替代这些测试。

不在此阶段继续做开放式技术探索。后续发现的新协议差异应按明确能力缺口处理，而非推倒整个架构。旧 Ali 服务保持独立，未来切换和迁移需要单独的测试、备份与回退方案。
